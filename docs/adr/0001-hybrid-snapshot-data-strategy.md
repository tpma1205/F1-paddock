# 採用「快照打底 + 執行期背景更新」的混合資料策略

三個資料來源（Jolpica-F1、OpenF1、f1-circuits GeoJSON）都免金鑰且 CORS 全開，因此本站可做成無後端的純靜態網站。資料取得有三種做法：純執行期打 API、純建置期快照、兩者混合。我們選擇混合——建置時抓取的 JSON 快照隨程式打包作為底稿，讓畫面秒開且在 API 失效時仍可完整顯示；載入後於背景靜默重打 API，成功才替換並標示資料更新時間。

## Considered Options

- **純執行期打 API**：資料最新，但首次載入需等網路、API 掛掉即空白，且 Jolpica 有約 500 次/小時的流量限制。
- **純建置期快照**：載入最快、最穩，但積分榜與倒數計時會凍結在建置當下，每次更新都要重新部署。
- **混合（採用）**：兼得秒開、永不空白與資料新鮮，代價是需額外維護一支抓取腳本，且要處理「快照與線上資料不一致」的顯示狀態。

## Consequences

- 需要一支 build 前執行的抓取腳本，並將產出的 JSON 納入版本控制。
- UI 必須能表達「資料來自快照」與「已更新至最新」兩種狀態，不可假裝資料永遠是即時的。
- 開發階段預設吃快照，避免每次熱重載都打第三方 API。

## 快照的更新機制

快照由 GitHub Actions 排程維護，**每週二（台灣時間）早上**自動抓取最新資料、建置並部署，另掛 `workflow_dispatch` 供手動觸發。純手動更新已被排除——它的失敗模式是人性的（會被遺忘），而本站的價值正建立在資料是新的。

- **抓到的資料不 commit 回 repo**，僅於建置當下使用，避免機器人 commit 污染歷史。repo 內的快照僅作為開發基準與離線底稿。
- **抓取失敗時沿用既有快照繼續建置**，不讓第三方 API 的暫時性故障導致整個部署失敗。Jolpica 由志工營運，暫時失效是可預期的。
- 排程選在週二，因正賽多在週日、少數在週六，週二可確保結果已定案。

## 已知的 Jolpica 相容性缺口

Jolpica 雖宣稱是 Ergast 的 drop-in 替代品，但**跨球季查詢強制要求 `season_year` 參數**：

```
GET /ergast/f1/driverstandings/1/  →  400 {"detail":"Missing one of the required parameters ['season_year']"}
```

Ergast 時代可一次取得歷年所有世界冠軍，在 Jolpica 必須逐年查詢（1950–2025 即 76 次請求）。**任何「跨球季」的功能都要先確認請求次數是否合理**——這是「歷年冠軍列表」未被納入範圍的直接原因。
